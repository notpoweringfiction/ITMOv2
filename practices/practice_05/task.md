# Десять небольших фич для своего проекта

**Выберите одну полезную идею; новый backend, продукт или framework не требуется.**

---

## Десять идей для улучшения

| **Контент и интерфейс** | **Ввод и действия** |
|---|---|
| 1. Фильтр существующего списка | 6. Проверка существующего ввода |
| 2. Поиск по имеющемуся контенту | 7. Экспорт видимых данных в файл |
| 3. Сортировка существующих элементов | 8. Одна локальная настройка |
| 4. Сброс фильтров или настроек | 9. Клавиша для существующего действия |
| 5. Копирование ссылки или результата | 10. Предпросмотр существующего изменения |

## Процесс разработки

**Шесть этапов от идеи к готовой фиче:**

Подготовка → **Исследование** → **Требования** → **Обсуждение** → **Код** → **Проверки** → **Архив** → **Настройка**

---

## Шаг 1. Выбираем фичу, исследуем и обсуждаем

**Небольшое улучшение своего проекта: фильтр, сортировка, поле ответа или проверка входа.**

### Команда в OpenCode

```
/opsx-explore
Хочу [небольшая фича моего проекта].
Прочитай затронутый код и существующие тесты.
Что уже есть? Что спорно или лишнее?
Найди команду проверки и запусти baseline.
Предложи узкие границы и вопросы для меня.
Код пока не меняй.
```

### Что делаете

- **Проверьте идею по коду:** что уже есть и что можно упростить.
- **Запишите 3–5 условий приёмки** и старое поведение, которое сохраняем.

**Готово:** выбрана фича; записаны 3–5 условий и то, что должно продолжить работать.

---

## Шаг 2. Создаём спецификацию

**Замените my-feature коротким именем своей фичи.**

### Команда в OpenCode

```
/opsx-propose my-feature
Цель: [одна фича моего проекта].
Используй выводы explore и принятые решения.
Зафиксируй 3–5 условий, ошибки и границы.
Сохрани согласованное прежнее поведение.
Укажи, что не входит в изменение.
Подготовь документы. Остановись до apply.
```

### Что делаете

- **Передайте решения шага 1:** цель, условия, ошибки и границы.
- **Прочитайте предложение до разрешения на код.**

**Готово:** предложение описывает нужное поведение и способ его проверить.

---

## Просмотр созданных specs и changes

| **Команда** | **Назначение** |
|---|---|
| `openspec list` | Показать все changes |
| `openspec list --specs` | Показать все specs |
| `openspec show CHANGE --type change` | Просмотр конкретного change |
| `openspec validate CHANGE --type change --strict --no-interactive` | Проверить документы |
| `openspec view` | Текстовый обзор |

**Примечание:** CHANGE берите из `list`; SPEC — из `list --specs`. Если SPEC есть в списке: `openspec show SPEC --type spec`.

## Шаг 3. Проверяем и уточняем решение

**Сначала отдельный проверяющий чат или агент. Затем решение человека.**

### Проверяющий чат

```
# Отдельный чат / агент-ревьюер
Прочитай предложение my-feature и связанный код.
Проверь цель, допущения, ошибки и совместимость.
Покажи конкретные пробелы. Файлы не меняй.
```

### Если нужно уточнение

```
/opsx-update my-feature
Учти согласованное решение: [уточнение].
```

**В Codex:** вызывает `$openspec-update-change my-feature`

### Что делаете

- **Разберите замечания;** не требуйте выдуманных ошибок.
- **Примите решения** и обновите спеку.

**Готово:** вопросы разобраны; вы прочитали итог и разрешили apply.

---

## Шаг 4. Реализуем фичу

**Запускайте apply после принятия спецификации.**

### Команда в OpenCode

```
/opsx-apply my-feature
Реализуй согласованное изменение.
Используй архитектуру и проверки проекта.
Не расширяй границы задачи.
При новом решении сначала обсуди его со мной.
Покажи изменения и результаты проверок.
Остановись до archive.
```

### Что делаете

- **Следите за границами задачи.** Если spec неверна или появились новые факты — остановите код и согласуйте правку.
- **Обновите документы:** `/opsx-update my-feature` (в Codex: `$openspec-update-change my-feature`). Прочитайте и примите diff; затем apply и проверки.

**Готово:** есть код, просмотренные изменения и фактические результаты проверок.

## Шаг 5. Проверяем и принимаем результат

**Используйте настоящую команду проверки своего проекта.**

### Отдельный проверяющий чат

```
Прочитай требования my-feature и изменения.
Найди и запусти команду проверки этого проекта.
Проверь основной, ошибочный и старый сценарии.
По каждому: ожидание → факт → доказательство.
Файлы не меняй.
Не считай отчёт автора самостоятельной проверкой.
```

### Что делаете

- **Разберите результат независимой проверки** и исправьте существенное.
- **Человек сопоставляет условия и факт;** к шагу 6 переходим после приёмки.

**Готово:** условия проверены; вы можете объяснить, почему принимаете фичу.

## Шаг 6. Обновляем specs и архивируем

**Только после приёмки человеком.**

### Команды в OpenCode

```
/opsx-sync my-feature
Покажи diff текущей спецификации.
Сверь её с принятым поведением.

/opsx-archive my-feature
Покажи main specs и запись в archive.
```

**В Codex:** `$openspec-sync-specs`, затем `$openspec-archive-change`

### Что делаете

- **Проверьте, что main spec описывает принятое поведение.**

**Готово:** текущая спецификация актуальна, завершённое изменение сохранено в истории.

## Часть 2. Настраиваем OpenSpec под себя

**77–90 минут · Один раз задаём правило проекта; проверяем его на одном фрагменте.**

### Сейчас

1. **Сохраним фрагмент «до» и постоянное правило проекта.**
2. **Проверим действие правила на этом фрагменте.**

### Готово, когда

- ☐ **Правило остаётся в config для следующих изменений.**
- ☐ **Diff принят человеком; смысл фрагмента сохранён.**

---

## Шаг 7. Добавляем правило OpenSpec для проекта

**Один раз сохраняем правило проекта; OpenSpec включает его в будущие инструкции.**

### Команда в OpenCode

```
/opsx-propose my-next-feature
Цель: [связанная фича]. Остановись до apply.
# Сохраните существующий фрагмент «до»
# Объедините с текущим openspec/config.yaml:
rules:
  design:
    - Объясни взаимодействие диаграммой Mermaid.
```

### Что делаете

- **Дополните текущий rules;** второй rules не создаём.
- **Правило действует для будущих design проекта;** design нужен не всегда.
- **Если design нет:** используйте `rules.specs` и Given/When/Then для существующей spec.

**Готово:** правило сохранено для будущих design; фрагмент «до» нужен для проверки.

---

## Шаг 8. Меняем форму и проверяем смысл

**Сначала свежие инструкции, затем предлагаемый diff и подтверждение человека.**

### Команда в OpenCode

```
/opsx-update my-next-feature
Перед правкой выполни в shell:
openspec instructions design --change my-next-feature --json
Проверь в ответе моё актуальное правило.
Примени его к тому же фрагменту; покажи diff.
Сохрани смысл и границы; правь после подтверждения.
Код не меняй.
```

### Что делаете

- **Для spec:** в CLI укажите `specs`, в config — `rules.specs`; назовите свой файл.
- **После подтверждения сравните до/после;** Mermaid откройте как диаграмму.

**Готово:** правило проверено на одном draft и остаётся для следующих изменений проекта.

## ДЗ 5 · Две команды — одна фича

**Выберите другой SDD-фреймворк и согласуйте две спецификации до генерации кода.**

| **За что** | **Баллы** |
|---|---|
| Другой SDD-фреймворк (применение и сравнение с OpenSpec) | **2** |
| Две спецификации (UI и логика, согласованные до кода) | **2** |
| Реализация (работающие UI и логика, сквозные проверки) | **5** |
| Рефлексия (что согласовали и чему научились) | **1** |

**Максимум: 10 баллов · Решения принимает человек**

### Структура

- **Команда 1 — Спека UI:** экраны, действия, состояния и ошибки.
- **Команда 2 — Спека логики:** данные, алгоритм, правила и API.
- **Согласуйте общий контракт:** сверьте данные, вызовы, ошибки и состояния.
- **После согласования:** реализация → сквозной сценарий и проверка ошибки / границы.

**Сдача:** спеки до/после, общий контракт, код, проверки и короткое демо.
