# Отчёт: локальные модели

Отчёт ведёт OpenCode по фактическим результатам команд и вашим сообщениям в чате. Поручите агенту заполнить разделы и показать diff. Выводы студента он записывает после обсуждения; отсутствующие измерения отмечает как невыполненные.

## Окружение

ОС / CPU / GPU / RAM / VRAM / свободный диск: Ubuntu 24.04.3 LTS в WSL2 (kernel 6.18.33.2-microsoft-standard-WSL2) / Intel Core i5-8265U @1.60GHz, 8 логических ядер (4 физических) / GPU не обнаружена — `lspci`/`nvidia-smi` недоступны из WSL, Ollama сама определила `library=cpu`, inference только на CPU / RAM всего 3.7 GiB (WSL2 лимит), доступно ~2.6 GiB в состоянии покоя / VRAM: нет (CPU-only) / свободный диск: 944 GB на `/`.
Ollama или LM Studio / OpenCode / Python, версии: Ollama 0.34.4 / OpenCode 1.18.33 / Python 3.12.3, make GNU 4.3, curl 8.5.0.
Модель, разработчик, семейство, тег и ID: Qwen3.5 (Alibaba/Qwen), тег `qwen3.5:0.8b`, id `f3817196d142`. Рабочие копии: `itmo-local` (id `8bf3cfdee3f6`, temperature 0.2, SYSTEM из Modelfile) и `itmo-agent` (id `06e253370071`, num_ctx 65536, без SYSTEM).
Формат, квантизация, лицензия, источник: GGUF, Q8_0, Apache License 2.0, скачано из `ollama.com/library/qwen3.5`. Параметров: 873.44M.
Фактический контекст, размещение CPU/GPU: `itmo-local` — 4096 (из Modelfile), `itmo-agent` — 65536 (подтверждено `ollama ps`: `CONTEXT 65536`). Размещение — 100% CPU (`ollama ps` → `PROCESSOR 100% CPU`), GPU не участвует.
Почему выбрана эта конфигурация: изначально пробовали `qwen3.5:2b` и начали загрузку `qwen3.5:4b`, но при 3.7 GiB RAM (WSL2) процесс `llama-server` для 2b с контекстом 65536 был убит OOM-killer'ом (см. `dmesg`: `Out of memory: Killed process ... llama-server`), а `qwen3.5:4b` создавала риск повторного OOM и не была даже полностью скачана. Переключились на `qwen3.5:0.8b` — самая маленькая модель линейки Qwen3.5, рекомендованная в PREPARATION.md для 8 GB RAM CPU-класса устройств. С 0.8b обе конфигурации (num_ctx 4096 и 65536) стабильно загружаются и отвечают без OOM, скорость декодирования выросла с ~6–10 tok/s (2b) до ~15–19 tok/s (0.8b).

## Воспроизведение

Команды и файлы конфигурации: `practices/practice_03/lab/Modelfile` (FROM qwen3.5:0.8b, num_ctx 4096, temperature 0.2, SYSTEM), `Modelfile.agent` (FROM qwen3.5:0.8b, num_ctx 65536, temperature 0.2, без SYSTEM), `demo/opencode.json` (провайдер `ollama` через `@ai-sdk/openai-compatible`, `baseURL: http://localhost:11434/v1`, модель `itmo-agent`, агент `local-guide` read-only). Сборка: `ollama create itmo-local -f Modelfile`, `ollama create itmo-agent -f Modelfile.agent`.
Подтверждение локального endpoint и скачанных весов: `curl --fail http://localhost:11434/api/tags` возвращает список моделей с digest'ами (`itmo-local:latest` 8bf3cfdee3f6, `itmo-agent:latest` 06e253370071, `qwen3.5:0.8b` f3817196d142) — все запросы идут на `127.0.0.1:11434`, без внешней сети.
Проверка без сети после подготовки: не выполнена отдельно (не было прав `sudo` без пароля, чтобы изменить `OLLAMA_NO_CLOUD=1` в systemd-юните `ollama.service` и перезапустить сервис). Косвенное подтверждение локальности — все запросы идут на `127.0.0.1:11434`, а `demo/opencode.json` теперь дополнительно ограничен `"enabled_providers": ["ollama"]`, что запрещает тестируемому агенту `local-guide` использовать любые внешние провайдеры.
Если работали в паре, чей компьютер и почему: практика выполнена на одном устройстве (не в паре); контекст 65536 у 0.8b модели вписался в 3.7 GiB RAM без перехода на компьютер партнёра.

## Скорость

Холодный старт отдельно: не измерялся отдельным прогоном «холодный vs прогретый» в рамках A/B (все 6 запросов temp-sweep выполнялись последовательно с уже загруженной моделью — `load_seconds` во всех файлах результатов ≤ 0.002 с, то есть модель была резидентна в памяти Ollama на всех замерах). Отдельно зафиксирован «первый запуск» модели `itmo-agent` с контекстом 65536: `load_duration=33.3s`, `total_duration=36.6s` (см. `results/agent-ready.json` в истории — модель грузилась впервые в память).
Три прогретых повтора и медиана (по `results/hotNN.json`, `results/coldNN.json`, метрики из `experiment.py`):

| Конфигурация | seed 42 | seed 43 | seed 44 | Медиана total_seconds | Медиана decode tok/s |
|---|---|---|---|---|---|
| temperature 0.2 (cold) | 0.588s / 18.57 tok/s | 0.621s / 17.21 tok/s | 0.642s / 17.00 tok/s | **0.621 s** | **17.21 tok/s** |
| temperature 0.8 (hot) | 2.356s / 16.00 tok/s | 0.992s / 12.97 tok/s | 3.669s / 14.39 tok/s | **2.356 s** | **14.39 tok/s** |

Единицы и метод замера: секунды (`total_seconds` = `total_duration` от Ollama API / 1e9), скорость — `decode_tokens_per_second` = `eval_count / (eval_duration/1e9)`. Метод — скрипт `experiment.py`, три отдельные вызова с `--seed 42/43/44` на каждую температуру, значения не усреднялись, а взята медиана из 3 точек.
TTFT измерен или не измерен: не измерен — `experiment.py` использует `stream:false` (нестриминговый ответ), поэтому "время до первого токена" технически неотличимо от полного времени ответа; это явно отмечено в PRACTICE.md как известное ограничение скрипта.

## Вывод

Ошибка или обнаруженное ограничение:
1. **Логическая ошибка модели на вопросе про персистентность** (см. `results/q5-error-example.jsonl`): при повторном запуске того же вопроса «Сохраняются ли подписки после перезапуска процесса?» модель `itmo-agent` (0.8b, ctx 65536, через OpenCode `local-guide`) успешно вызвала `read` на правильный файл `service.py`, но сделала неверный логический вывод: *«Да, подписки сохраняются после перезапуска процесса. Код не хранит историю подписок в памяти... этот словарь обновляется только при вызове subscribe() и всегда остается на месте после перезапуска»* — это прямое противоречие факту `subscribers = set()` (in-memory) и явному тексту README.md («Подписчики хранятся в памяти процесса»). При повторном прогоне того же вопроса (`results/q5.jsonl`) модель дала верный ответ «Нет... подписки не сохраняются». Ошибка нестабильна (модель иногда права, иногда нет), что типично для маленькой 0.8B модели без reasoning.
2. **Галлюцинация путей файлов при tool calling**: в нескольких попытках (см. временные прогоны `read-check`/`q1`) модель выдумывала несуществующие абсолютные пути (`/Mnt/c/...` с неверным регистром, `/usr/share/nginx/html/README.md`, `/app/Itmo-DS-SE/...`, `/root/.ssh-agent`) вместо переданного в задаче реального пути проекта. Из ~9 попыток вызвать `read`/`glob` с абсолютным путём проекта успешными были ориентировочно 40–50%; при неудаче модель либо просила уточнить путь, либо выдумывала несвязанный контент (например, ответ про React/TypeScript на вопрос про Python-репозиторий).
3. **Скрытая проблема конфигурации `think`**: параметр `think:false`, задокументированный в PRACTICE.md, не передаётся из OpenCode через провайдер `@ai-sdk/openai-compatible` (используется `/v1/chat/completions`, который игнорирует top-level `think`). Из-за этого первые попытки подключить `itmo-agent` к OpenCode с контекстом 65536 приводили к тому, что модель уходила в бесконечное "thinking" на CPU (один прогон был прерван после 36+ минут занятого CPU без ответа). Исправлено добавлением `"options": {"reasoningEffort": "none"}` в `demo/opencode.json` для модели `itmo-agent` — это поле AI SDK транслирует в `reasoning_effort` тела запроса, которое Ollama корректно распознаёт для отключения thinking у Qwen3.5.

Как проверили: пункт 1 — повторный запуск одного и того же вопроса в отдельных сессиях `opencode run` (без продолжения контекста), сравнение текста ответа с фактическим кодом `demo/service.py:1` (`subscribers = set()`) и `demo/README.md:2`. Пункт 2 — серия из 3 повторов на несколько вопросов, сверка поля `state.input.filePath` в `tool_use` событиях JSON-вывода с реальным путём проекта. Пункт 3 — сравнение прямых `curl` запросов к `/api/chat` (нативный Ollama API, `think:false` работает) и `/v1/chat/completions` (OpenAI-совместимый, `think` игнорируется, но `reasoning_effort` работает), проверено многократными повторами.

Какой конфигурацией будете пользоваться: `qwen3.5:0.8b` с `temperature=0.2` для локальных экспериментов (`itmo-local`) — низкая температура стабильно давала честные ответы «нет данных» на все 3 seed без единой ошибки, в отличие от `temperature=0.8`, где 1 из 3 ответов содержал недопустимое категоричное утверждение. Для агентного сценария в OpenCode — `itmo-agent` с `num_ctx=65536` и обязательным `reasoningEffort: "none"` в конфиге провайдера (без этого агент на слабом CPU не отвечает за разумное время).

Что осталось непроверенным:
- Полная сетевая изоляция (`OLLAMA_NO_CLOUD=1` на уровне systemd-сервиса) — не удалось перезапустить `ollama.service` без пароля `sudo` в неинтерактивном режиме; частично компенсировано через `enabled_providers: ["ollama"]` в `demo/opencode.json`, что ограничивает именно тестируемого агента `local-guide`.
- Реальное измерение TTFT (стриминговый ответ) — `experiment.py` работает только в режиме `stream:false`.
- Сравнение с моделью Gemma3 на практике — только по карточкам моделей (раздел «Сравнение семейств»), веса Gemma3 не скачивались.
- Статистически надёжная оценка процента успешных tool calls у 0.8b модели — оценка «40–50%» основана на выборке около 9 попыток, а не на большом прогоне.
